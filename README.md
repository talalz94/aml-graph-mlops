# AML graph MLOps

[![CI](https://github.com/talalz94/aml-graph-mlops/actions/workflows/ci.yml/badge.svg)](https://github.com/talalz94/aml-graph-mlops/actions/workflows/ci.yml)

Anti money laundering transaction monitoring, built and measured the way a bank runs it: classic monitoring rules first, then machine learning on graph features, all judged on how much laundering an investigation team catches with the alerts it can actually review each day.

It runs on IBM's AMLworld, a public benchmark of fully synthetic bank transactions with labelled laundering (5 million transactions in the HI-Small set). Features are built with PySpark; the models run on a laptop CPU.

**Why this repo exists.** I tuned AML detection scenarios on more than 100 million bank transactions, with segment level thresholds and simulation, and ran the MLOps behind production models. That work is private, so this is a public rebuild of the same problem on open synthetic data, written from scratch. No bank, client or employer data, code or details are in here.

**Status.** Slice 1 (features, rules, LightGBM, metrics) is built and tested on generated data. Results on AMLworld appear below once the data is downloaded and `uv run poe reproduce` has run; numbers from generated data are never shown.

## Quickstart

You need [uv](https://docs.astral.sh/uv/) and Java 17 or newer (for PySpark).

```bash
git clone https://github.com/talalz94/aml-graph-mlops.git
cd aml-graph-mlops
uv run poe demo        # the whole pipeline on a small generated dataset, no download
```

The demo writes its scores to `data/results/`, which git ignores. Scores on generated data are kept away from `results/`, the folder the Results table is built from: they go under `data/` unless you pass `--results-dir`, `aml report` never renders them, and git ignores `results/SYN/` as well.

For the real data, either set `KAGGLE_USERNAME` and `KAGGLE_KEY` in your environment (from your Kaggle account settings) and run `uv run aml download`, or download `HI-Small_Trans.csv` and `HI-Small_Patterns.txt` from the [Kaggle page](https://www.kaggle.com/datasets/ealtman2019/ibm-transactions-for-anti-money-laundering-aml) and run `uv run aml import FILE` for each. A zip from that page works too: `uv run aml import FILE.zip` takes the HI-Small files out of it (add `--dataset` for another set). Then:

```bash
uv run poe reproduce   # rebuilds the features, evaluates every system, rewrites the tables above
```

## How it works

- **Batch monitoring view.** Banks review alerts the day after, so a transaction's features may use its whole day and the days before, never a later day and never a label. Unit tests check this on generated data: cutting the file after each of its days leaves the features of every transaction up to that day unchanged, and shuffling the labels across rows changes no feature.
- **Amounts in US Dollar.** Each currency's rate on a day is the median US Dollar rate over the rows that pair it with US Dollar on or before that day, and 1.0 until such a row exists. Money out is counted in paid amounts, money in in received amounts.
- **Self transfers.** A payment from an account to itself moves no money between accounts. It is left out of the account totals, the pair counts and the 2 cycle check, no rule ever alerts on it, and the `self_loop` feature marks it.
- **Features (PySpark).** For the sender and the receiver: the day's in and out counts and sums, and the pass through ratio (money out over money in). For the sender, its distinct receivers that day (fan out), and daily averages over the 7 days before of its payments out and distinct receivers; for the receiver, its distinct senders that day (fan in), and daily averages over the 7 days before of its payments in and distinct senders. The averages count only the days the file covers, so from the file's second day on they share one scale; on the first day there is no history, and they are left missing rather than set to zero. Per transaction: a payment from the receiver to the sender on the same or the previous day (2 cycles), repeated pairs, amount, payment and receiving currency, currency and bank crossings, self payments, payment format and hour.
- **Temporal split.** 60/20/20 by time in whole calendar days, with the two cut days chosen by the rule in IBM's Multi-GNN code: the pair of days whose worst relative miss on the three shares is smallest. Late transactions after the main period are all laundering in the Kaggle release, so they are dropped rather than left to leak the label through the timestamp. The paper's test split keeps them, so its test set is not this repo's.
- **Systems.** Monitoring rules with default thresholds; the same rules with thresholds tuned per payment format segment on the train period; LightGBM on the features, with early stopping on the dev period's average precision. Tuning tries the default threshold and every train value above it, and keeps, for each segment and rule, the one that raises the fewest train alerts while still catching at least 90% of the train laundering the default threshold catches; the default itself always qualifies. With its default threshold, a pass through rule fires when the day's money out is between 90% and 111% of the money in, with at least 1,000 US Dollar coming in; a tuned threshold narrows that band from both sides.
- **Metrics.** Minority class F1 (the paper's headline metric, measured on this repo's own split): LightGBM at the threshold with the best F1 on the dev period, the rules at their own alerts, whenever any rule fires. Also PR-AUC, recall at 50, 100 and 500 alerts a day (for the rules only their own alerts fill the budget, so a day with fewer alerts leaves the rest of it unused), and recall per laundering pattern at 100 alerts a day. The column "Alerts (recall) vs tuned rules" sets each system's test alerts and recall beside the tuned rules' own: the rules at their own alerts, LightGBM at a cut set on the dev period to reach the tuned rules' recall there.
- **Traceable results.** `aml features` saves a stamp next to the feature table with the raw file's SHA-256, the period end and a hash of the feature code, and every result file carries it, along with a hash of the whole package and the patterns file's SHA-256. `aml eval` rebuilds the table when the stamp no longer matches, `aml reproduce` always rebuilds it, and `aml report` refuses to put results from different builds in one table.
